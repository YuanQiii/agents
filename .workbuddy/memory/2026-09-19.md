**1. typecheck 的 13 个错误全部同源，均属环境问题。** 根 `node_modules/axios` 是**空壳**（`existsSync` 为 false），

虚拟店 `.pnpm/<pkg>@*/node_modules/<pkg>/` 里包完好。=> 重跑 `pnpm install` 即可。

**4. `oxlint` 的 `patterns` 分支补测通过**（昨天只测了 `paths`）：临时目录里 `no-restricted-imports` 的
`patterns` + `overrides[].files` 正确触发，报错带自定义 message。至此两条边界规则的两个分支都有实证。

**5. 依赖声明数更正**：包间依赖实测是 **7 条 / 5 个包**，不是此前记的 6 条。

**7. 发现并修掉一个 Gate 静默失效（本轮最重要的技术发现）。** 用户授权后改 `.oxlintrc.json`：
两条 `overrides` 同时命中 `src/views/**`，而 **oxlint 的 override 不是合并、而是后条整体覆盖前条**，

四个用例复测全部符合设计（views+axios 报、layouts+axios 报、views 互引报、layouts 引 views 不报＝语义未变）。

（`§` 计数已归零）。该陷阱已写入 `docs/guides/architecture.md` 模块边界与技能的「以为 override 是叠加的」反模式行。

## 术语追问consecutive 三轮：docs/guides 性质、代码内联契约、约束骨架

用户连续问三个词，每次都是「我（或提示词）用过但没定义清楚」的词。查证结论：

1. **`docs/guides/` 是规范还是事实** → **事实为主**（6 篇 44 节里 5 篇以事实为主，只有 `conventions.md` 以规范为主）。
   但真正该用的判据不是「规范 or 事实」，而是**「环境能不能表达」**：能表达的（格式化参数、scripts 全表、
   tsconfig 取值、目录树）两者都不写；表达不了的规范与事实都写。这也印证了不叫 `rules/` 的决定。
2. **「代码内联契约」** → **这个词不是既有概念，方向还被混了两次**。原提示词里「Contract 应优先通过
   Type → Schema → Runtime Validation → Assertion → Test → Architecture Rule 实现」与「不要为普通函数批量加
   `// CONTRACT:` 注释」是**相反**的两句话。查证本仓库：`CONTRACT` 字样 **0 处**；契约实际分布在
   类型（最常用）→ 无 Schema（ADR-0003）→ **8 处 `throw new Error`** → 无测试（ADR-0002）→ 2 条 lint 架构规则 →
   **注释型仅 1 处**（`src/service/request/index.ts:87` 的 refreshToken 死循环）+ 1 处 `@deprecated`。
   注释型契约的唯一成立条件是「机器表达不了 + 后果严重」，且必须同时登记进 guides 的不变量表。
3. **「约束骨架」** → **这个词全库与技能里都不存在**，我用过「骨架」只在 `docs/agents-md-audit.md:15`
   （「骨架是健康的」）。把它定义清楚：**约束体系的「必须存在哪些槽位 + 怎么连接」，回答「缺什么」而非「对不对」**。
   关键区分：**槽位缺失是结构问题（改一句话救不了），槽位填错是事实问题**；反之，一份每句都对的文档
   也可能骨架是坏的（把 60% 内容塞根文件：每句不错，但每次会话读全文）。

**技能优化（本轮的实质产出）**：用户第 3 问暴露了 `write-agents-md` 的真缺口——它的审计步骤**只审内容、
没有「先过骨架」**，而「骨架先于内容」正是 soybean 那次审计的核心结论。已补三处（现 147 行，复验 valid）：
① 步骤 6 改为「分两遍，顺序不能反：先过骨架 → 再过内容」，完成判据加入骨架结论；
② 判定规则新增**骨架三问**（只看根文件底线守得住吗 / 根文件有无「按分支才用」的段落 / 每条规则是否只有一个主场）；
③ 提示词模板同步。

## 追问「怎么做比较好」→ 研究社区的防腐烂体系

**研究来源**：`agentslint`（GitHub `giacomo/agents-lint`，真实工具）、agentsurface.dev 的 drift-detection、
thepromptshelf / reasoncore 的 CI 与 PR 匹配检查。均为二手，但内容互相印证且有可落地细节。

**社区把防腐分成四层（+1）**：
1. **写作纪律**（最有效）：`if it isn't in the repo, it doesn't go in the AGENTS.md`；命令跑过再粘；
   **指配置、不抄规则**——抄下来的取值就是会随配置失真的话。
2. **PR 级漂移检测**（治「缺失型」）：watchlist（`package.json`、lock、`*.config.*`、`.env.example`）
   变了而 `AGENTS.md` 没变就提示/拦下；原文规则「**it changes in the same PR as the code**」。
3. **内容级 CI 检查**（治「指针型」）：即我们已经做的 `agents-check`。
4. **定期复核**（治「文件没动但代码变了」）：挂 cron 每周；「腐烂发生在文件没变的时候」。
5. **代理级验证**（proof loop）：把 agent 指向文件、看它是否真的照命令干活。

## 回答「PR 级漂移检测是什么」+ 五层防腐的落地方案（产出 docs/anti-rot-plan.md）
