> **状态：提案，待批准。** 本文是一次性评估记录 + 落地方案，**不是现状描述**——批准与落地后请改写「三、结论」与「四、方案」两节，或把结论转成 ADR-0004。

> 评估对象：`agents-lint@0.5.0`（npm，MIT，零依赖，`engines: node >= 18`）。
> 本文所有关于该工具行为的陈述均在 **2026-09-19 于本仓库逐文件实测**，与它 README 不符之处已单独标注。

## 一、PR 级漂移检测是什么

**定义**：把「代码侧的文件变了」与「文档侧的文件变了」当作一对关系来检查——当 watchlist 里的文件在一个 PR 中被修改，而同一个 PR 里没有任何约束文档被修改时，发出提醒。

**它与内容检查的区别不在检查什么，而在触发条件**：

|          | 内容检查（第 3 层）             | PR 级漂移检测（第 2 层）       |
| -------- | ------------------------------- | ------------------------------ |
| 输入     | 文档当前的文本                  | 一次 PR 的 `git diff`          |
| 问的问题 | 「文档里写的路径/命令还成立吗」 | 「代码改了，文档有没有跟上」   |
| 能发现的 | 已经写错的内容                  | **尚未写错、但即将失效的内容** |
| 误报来源 | 工具的假设与仓库惯例不符        | watchlist 划分不准             |

两者互补，因为**它们抓的是不同时刻的腐烂**：漂移检测抓「同步失败」，内容检查抓「同步失败之后遗留的错」。一个 PR 改了 `package.json` 里的脚本名而文档没跟上——漂移检测在合并前就说话；如果它没被拦住，一周后内容检查才可能发现。

**作用**：把「文档更新」从「想起来才做」变成 PR 评审时的一个可见项。它**不阻断**——硬拦会逼人做无意义的空改动，比不提醒更糟。

**本仓库已有实现**：`.github/workflows/agents-md-drift.yml`。判据 12 条真值用例已实测（只改 `package.json` → 触发；`package.json` + `AGENTS.md` → 不触发；`packages/materials/src/index.ts` → 不触发；`packages/axios/tsconfig.json` → 触发；`.github/workflows/*` → 不触发）。用 `gh` CLI 留言、带 marker 只留一条、问题解决后自动删除。

**注意**：`agents-lint` **不提供这一层**。它的触发条件永远是「文件当前内容」，没有任何关于 `git diff` 的概念。

| `CONTEXT.md`                         |    0 |     2 |                                                                           |
| `docs/guides/api.md`                 |    0 |     2 |                                                                           |

**合计 18 个 error，全部是 `filesystem:no-missing-path`——逐条核对后 18/18 均为误报。** 四类：

1. **URL / 代理前缀被当成文件路径**（7 条）：`/proxy-default`、`/proxy-${key}`、`/login/:module(pwd-login|code-login|…)`、`/oc`、`/opencode`
2. **包的 `exports` 子路径被当成文件路径**（3 条）：`./fetch`、`./client`、`./mock`（`packages/AGENTS.md` 在讲 `@sa/alova` 的子路径导出）
3. **tsconfig 路径别名被当成文件路径**（2 条）：`./*`、`./src/*`
4. **正确的相对 markdown 链接被判为不存在**（6 条）：如 `docs/guides/conventions.md` 里的 `../../packages/AGENTS.md`。它按**仓库根**解析，而不是按**文件所在目录**解析——本仓库 `agents-check` 校验的 41 条相对链接全部可达，同一批链接被它判为坏的。

另有一条 `no-missing-script`：把 `docs/guides/workflow-validation.md:113` 里 `pnpm --version` 的 `--version` 当成了不存在的 script。

**结论：它在唯一有意义的检查项（路径/命令）上，对本仓库 0 真问题、19 个误报（18 路径 + 1 命令）。**

### 工具行为与其 README 不符之处（均已实测）

| README 说                             | 实测                                                                                                                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 退出码 `1 = Warnings or errors found` | **3 条 warning 时退出码为 0**。只有显式 `--max-warnings 0` 才返回 1——按 README 的模板接进 CI，会得到一个「报告了腐烂却显示绿色」的检查                                                     |
| `Custom rules (.agents-lint.json)`    | 名不副实：**没有规则作者接口**。只有 4 项可配：`requiredSections` / `ignorePatterns` / `severity.{missingPath,missingScript,staleDependency,missingSection}`。**无法禁用任何一个内置规则** |
| 扣分表 error 15 / warn 7 / info 2     | 对不上：3 条 warn 得 65 分（按表应 79），5 条 warn 得 25 分（按表应 65）。公式未公开且非线性                                                                                               |
| `--format json`                       | **两种形状**：自动发现时 `{files, reports[]}`；显式传文件时 `{file, score, results, totalIssues, errors, warnings, infos, timestamp}`。消费方必须同时处理                                  |

实测生效的两项：`ignorePatterns: ["drizzle"]` 能抑制该条依赖误报；`severity.missingScript: "info"` 能把 `no-missing-script` 降级——但**不控制 `missing-test-script`**，同属 Npm Scripts 段的两条 finding 只有一条可配。

**关键推论**：因为配置无法禁用内置规则，任何采纳都必须**外挂一层按 `rule` ID 过滤的包装器**，而不是靠 `.agents-lint.json`。

## 三、结论：agents-lint 不是「五层防腐」的载体

「在 agents-lint 中实现五层防腐」这个命题不成立——**它没有规则作者接口**。它能做的只有三件事：加必须存在的章节名（`requiredSections`）、排除子串（`ignorePatterns`）、调四类严重度（`severity`）。

正确的关系是：**五层各有自己的承载物，agents-lint 只是第 3 层里的一个可选的第二意见。**

| 层              | 触发信号       | 承载物                                      | agents-lint 的覆盖               |
| --------------- | -------------- | ------------------------------------------- | -------------------------------- |
| ① 写作纪律      | 无             | 人 + `write-agents-md` 技能                 | 无法表达                         |
| ② PR 级漂移检测 | `git diff`     | `agents-md-drift.yml`                       | 无 diff 概念                     |
| ③ 内容检查      | 文件当前内容   | `check-agents-md.mjs`（+ 可选 agents-lint） | **唯一主场**                     |
| ④ 定期复核      | 时间           | `linter.yml` 的 `schedule`                  | 只贡献了 `schedule` 的 YAML 写法 |
| ⑤ 代理级验证    | agent 实际行为 | 尚无                                        | 做不到                           |

**实施状态**：① ② ③ ④ **已落地**；⑤ 仍未做（见该节的理由）。
`docs/anti-rot-plan.md` 本身是方案文档，**状态以这一行为准**。

## 四、逐层方案

### 第 ① 层 · 写作纪律

|              |                                                                                                                                            |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **目标**     | 让会腐烂的内容从一开始就不被写进去——这是唯一能治「缺失型腐烂」的一层                                                                       |
| **检查内容** | ① 是否抄了配置能表达的值（格式化参数、scripts 全表、版本号、目录树）；② 是否写了会变的状态（「当前 PASS/FAIL」）；③ 同一条规则是否出现两处 |
| **约束条件** | 无自动信号，只能靠人和技能；不能改由工具代劳                                                                                               |
| **预期输出** | 写完后过一遍上述三条；`pnpm agents-check` 的「无章节号指针」项作为机械化兜底                                                               |

**落地与验证**：已在 `write-agents-md` 技能（步骤 1 取证、步骤 5 收口、步骤 6 审计）。验证方式是**回看实证**——本仓库已发生两次：`workflow-validation.md` 早期写过「typecheck 当前 FAIL」这类状态描述（已改成「症状→根因→处置」），`conventions.md` 一度把共享 ESLint 配置的取值抄成表格（已标注「本文件里唯一会随依赖升级失效的部分」）。

### 第 ② 层 · PR 级漂移检测

|              |                                                                                                                                                                                                                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **目标**     | 代码侧 watchlist 变了而文档没跟上时，在 PR 上留一条可被忽略的提醒                                                                                                                                                                                                                                                   |
| **检查内容** | watchlist：`package.json` · `pnpm-lock.yaml` · `pnpm-workspace.yaml` · `eslint.config.js` · `.oxlintrc.json` · `.oxfmtrc.json` · `tsconfig.json` · `vite.config.ts` · `uno.config.ts` · `.env*` · `packages/*/package.json` · `packages/*/tsconfig.json`。判据：命中任一 watchlist，且 PR 内无任何 `AGENTS.md` 改动 |
| **约束条件** | 只提醒不阻断（不得改变 CI 结论）；评论带 marker、只留一条、条件消失后自动删除；用预装的 `gh` CLI，不猜 action 版本；`gh` 失败时不得误报为「有漂移」                                                                                                                                                                 |
| **预期输出** | PR 上一条评论，列出「哪些 watchlist 文件变了」+「建议看哪份文档」；PR 无 watchlist 改动时静默                                                                                                                                                                                                                       |

**落地与验证**：`.github/workflows/agents-md-drift.yml`。验证已做——**12 条真值用例**覆盖触发与不触发两侧（含 `packages/materials/src/index.ts` 不触发、`packages/axios/tsconfig.json` 触发这类边界）。这类判定逻辑不测就等于没写：正则漏一个 `/` 会让它永远沉默。

### 第 ③ 层 · 内容检查

|              |                                                                                                           |
| ------------ | --------------------------------------------------------------------------------------------------------- |
| **目标**     | 文档现在说的东西，在当前仓库里仍然成立                                                                    |
| **检查内容** | 相对链接可达 · 文档提到的命令真实存在 · 无章节号指针                                                      |
| **约束条件** | 零依赖、离线可跑（CI 里不装依赖）；**判据宁可漏报不可误报**（被误报的检查很快会被人关掉）；只读，不改文档 |
| **预期输出** | `pnpm agents-check` 退出码 0 / 1，逐条 FAIL 带 `文件:行`                                                  |

**落地与验证**：`scripts/check-agents-md.mjs` + `linter.yml` 的 `agents-md` job。验证方式是**故意违规探针**：放入坏链接、假命令、章节号指针三个探针后必须被三条检查分别拦下，删除探针后必须复绿（已实测；写作本文时它又抓到本文里的同一个写法，改的是文档而非检查）。

**若把 agents-lint 作为第二意见接入**（可选，见第五节）：

- 定位：独立的 weekly job，**只报告、不阻断**，不进 `pre-commit`
- 必须过滤的规则 ID（含理由）：
  - `missing-setup-section` / `missing-test-section` / `missing-build-section` — 英文标题假设，且根文件是刻意的路由器
  - `missing-test-script` — `ADR-0002` 已决定不建测试体系，工具的建议与既有决策直接冲突
  - `no-missing-path` — 本仓库 18/18 全误报（URL 前缀 / exports 子路径 / tsconfig 别名 / 相对链接基准错误）
  - `no-missing-script` — `pnpm --version` 这类 pnpm 内建被误判
  - `no-missing-dependency` — 仅在提及**否定语境**时忽略（本仓库的 `drizzle`、`zod` 都出现在「本仓库不存在」的句子里）
- 验证步骤：先跑一次拿全量 `rule` ID 基线 → 逐个判定「保留 / 忽略」并写明理由 → 保留项造一个故意违规文件确认真能触发 → 确认过滤后基线为 0

### 第 ④ 层 · 定期复核

|              |                                                                                                             |
| ------------ | ----------------------------------------------------------------------------------------------------------- |
| **目标**     | 文档没变、但周边代码变了导致的腐烂（本仓库真实发生过：手动跑链接校验时漏掉了根文件里不带 `./` 的链接）      |
| **检查内容** | 与第 ③ 层相同，区别只在触发条件是时间                                                                       |
| **约束条件** | 失败必须真的有人看到（否则等于没挂）；不与 PR 检查重复刷屏；加 `workflow_dispatch` 以便手动验证而不是等一周 |
| **预期输出** | 每周一次 job 结果；失败走 GitHub 默认通知                                                                   |

**落地与验证**：**已落地**——`.github/workflows/linter.yml` 加了 `schedule`（每周一 09:00 UTC）与 `workflow_dispatch`；
同时给 super-linter job 加了 `if: github.event_name != 'schedule'`，让每周那次只跑零依赖的约束文档检查，不必拉起 super-linter。
放在已有 workflow 里而不是新建一个，是为了不重复那条命令。

验证方式：本地跑一遍 `node scripts/check-agents-md.mjs` 确认结论（已完成，PASS）；**CI 侧用 `workflow_dispatch` 手动触发一次**确认真的跑起来并产出与本地一致的结论——不必等一周。

**agents-lint 在这一层的贡献只是 README 里那段 `schedule: cron` 的写法**，不是能力。

### 第 ⑤ 层 · 代理级验证

|              |                                                                                                                                            |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **目标**     | 文档写下的规则，agent 实际会不会照做                                                                                                       |
| **检查内容** | 给定文档 + 一个具体任务，观察 agent 是否遵守。例如「在 `src/views` 下直连 `axios`」看它是否拒绝、「新增一个 i18n key」看它是否同步中英两份 |
| **约束条件** | 成本高、结果不稳定（同一 prompt 两次可能不同）；只适合少量最贵的规则；不得进阻断路径                                                       |
| **预期输出** | 一份人工记录：哪条规则、哪天验证、结论                                                                                                     |

**落地与验证**：无自动承载物，`agents-lint` 完全做不到。最接近的现成替代是 `docs/v2-regression-checklist.md`（人工回归清单）。若要做，范围压到 3 条最贵的铁律（生成物不手改 / 四类改动先问维护者 / 边界不直连 HTTP），写成固定 prompt，季度跑一次并把结果追加进清单。

## 五、采纳方案（三档，需你选择）

| 档                       | 内容                                                                                                                                     | 代价                                                                             |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **A · 不引入**（推荐）   | 维持现状：自检脚本（第 ③ 层）+ 漂移检测（第 ② 层），并补第 ④ 层                                                                          | 放弃它唯一的增量（废弃依赖 / 体积 / 跨文件一致性），而这三项在本仓库当前都无命中 |
| **B · 作为周更第二意见** | 新增 `.agents-lint.json`（全 `ignorePatterns` + 严重度降级）+ `agents-lint` weekly workflow，**只报告不阻断**，用 JSON 按 `rule` ID 过滤 | 新增一个 devDependency；需联网；首搭要人工判定一遍过滤名单                       |
| **C · 引入并阻断**       | 同 B，但 `--max-warnings 0` 进 PR 检查                                                                                                   | **不推荐**：会因英文标题假设与相对链接基准错误长期红灯，最终被人关掉             |

**推荐的组合是 A + 补第 ④ 层**：本仓库已有 41 条链接、13 份文档、命令白名单的完整校验，且实测在它唯一有意义的检查项上 0 真问题；而它做不到的两件事（`§` 锚点、按文件解析相对链接）恰好是我们踩过坑的地方。

### 授权点（都属「改动前先问维护者」的范围）

1. 引入 `agents-lint` 为 devDependency —— **仅第 B / C 档需要**
2. 新增 `.agents-lint.json` 与 weekly workflow —— 同上
3. 给现有 workflow 加 `schedule` + `workflow_dispatch` —— 第 ④ 层需要

## 六、验收判据（落地后如何确认有效）

| 层  | 验收判据                                                                        |
| --- | ------------------------------------------------------------------------------- |
| ①   | 新增/改动的文档不含配置能表达的值，不含会变的状态描述；同一规则全仓只有一处定义 |
| ②   | 12 条真值用例全过；在一个真实 PR 上留言一次、补文档后评论消失                   |
| ③   | 故意违规探针被拦（坏链接 / 假命令 / `§` 指针各一），删除后复绿；退出码语义正确  |
| ④   | `workflow_dispatch` 手动触发成功，结论与本地一致                                |
| ⑤   | 3 条铁律各有一条人工验证记录，含日期与结论                                      |

**共同的一条**：每个检查都必须有一次「故意让它失败」的实证。`全仓 0 问题` 不能证明检查有效——它同样可能意味着检查被覆盖、作用域没匹配上，或者根本没跑。
